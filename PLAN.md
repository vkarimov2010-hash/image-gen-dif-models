# Веб-приложение для сравнения моделей генерации изображений (kie.ai)

_Первоначальный план работы (составлен в режиме планирования перед началом реализации)._

## Контекст

Задача: инструмент для выбора модели генерации изображений под конкретный проект. Пользователь один раз описывает промт и настройки изображения (стиль, размер, ориентация, назначение), сервис отправляет запрос сразу в несколько моделей на kie.ai, показывает результаты рядом для визуального сравнения, даёт скачать понравившиеся и показывает стоимость генерации. Сначала — личный инструмент, архитектура должна допускать рост до продакшна (мультипользовательский режим, масштабирование очереди задач, S3-хранилище) без переписывания с нуля.

Технический стек по итогам обсуждения: **React (Vite, TypeScript) + Python (FastAPI)**, база данных с историей/галереей с самого MVP, сгенерированные изображения скачиваются и хранятся у себя (не хотлинкаются с kie.ai — там ссылки могут быть временными). Набор моделей kie.ai не жёстко зашит в код — реализуется как расширяемый реестр, пользователь сам выбирает нужные модели в интерфейсе перед генерацией.

### Как устроено API kie.ai (по документации docs.kie.ai)
- Аутентификация: `Authorization: Bearer <API_KEY>`.
- Унифицированный паттерн для всех моделей: `POST /api/v1/jobs/createTask` (создать задачу генерации) → `GET /api/v1/jobs/recordInfo?taskId=...` (поллинг статуса/результата). Есть опциональные webhook-колбэки как альтернатива поллингу.
- Баланс кредитов аккаунта: `GET /api/v1/chat/credit`.
- У каждой модели (Flux-2, Google Imagen 4, Ideogram, Qwen, Z-image, Grok Imagine, Recraft, Topaz upscale и др.) — свой набор параметров запроса; единого эндпоинта со списком моделей нет, поэтому список моделей и маппинг параметров поддерживаем на своей стороне (реестр).
- Точный расход кредитов за конкретную задачу в ответе `recordInfo` документацией явно не гарантирован — по прайсу это ориентировочно 10–50 кредитов за генерацию в зависимости от модели. Стоимость будем оценивать по таблице цен модели (её нужно свериться на https://kie.ai/pricing при реализации) и уточнять фактический расход через дельту `/chat/credit` до/после батча.

## Архитектура

```
React (Vite/TS) SPA
        │  REST (+ поллинг статуса)
        ▼
FastAPI backend
   ├── /models        — реестр доступных моделей kie.ai (конфиг, расширяемый)
   ├── /generations    — создать батч генерации (промт+настройки+список моделей)
   ├── /generations/{id} — статус/результаты батча
   ├── /generations     — история с пагинацией и фильтрами
   ├── /images/{id}/download — отдать файл
   └── /credit          — текущий баланс kie.ai
        │
        ├── asyncio + httpx: параллельные вызовы createTask по всем выбранным моделям
        ├── фоновый поллинг recordInfo до готовности
        ├── скачивание готового изображения → Storage
        └── SQLAlchemy → PostgreSQL (история, батчи, задачи, реестр моделей)

Storage: абстракция StorageBackend — на MVP локальная файловая система
(volume в docker), интерфейс позволяет позже подключить S3/R2 без изменений
в бизнес-логике.
```

### Модель данных (PostgreSQL, через SQLAlchemy + Alembic)
- `models_registry`: id, provider slug, display_name, capabilities (стили/размеры, которые модель поддерживает), request template/param mapping, ориентировочная цена за генерацию, активна ли модель.
- `generation_batch`: id, prompt, style, size, orientation, purpose, created_at, status, суммарная стоимость.
- `generation_task`: id, batch_id, model_id, kie_task_id, status (pending/running/done/failed), image_path, cost_credits, cost_usd, error, duration.
- (Задел на будущее, не для MVP) `user`: под мультипользовательский режим в продакшне.

### Реестр моделей (ключевая часть для расширяемости)
Конфигурация в коде/БД, а не хардкод в UI: каждая запись описывает, как наши универсальные поля (style, size, orientation, purpose→aspect ratio) транслируются в параметры конкретной модели kie.ai. Добавление новой модели kie.ai = добавить одну запись в реестр, без изменений фронтенда. Это прямой ответ на пожелание «пусть пользователь сам выбирает модели» — UI всегда рендерит то, что есть в реестре бэкенда.

### Назначение изображения → пресеты размера/ориентации
"Пост в соцсети", "Аватар", "Telegram-канал (обложка)", "Story" и т.д. — заранее заданные пресеты (например Telegram-аватар 512×512, Instagram-пост 1080×1080, Story 1080×1920), которые автоматически подставляют размер/ориентацию, но пользователь может переопределить вручную.

### Параллельная генерация и статусы
Все выбранные модели запускаются одновременно (`asyncio.gather` + `httpx.AsyncClient`), а не по очереди — иначе сравнение 4-5 моделей растягивается на минуты последовательно. Фронтенд поллит `/generations/{id}` раз в 1-2 сек и обновляет карточки по мере готовности каждой модели независимо (не ждём самую медленную для показа остальных).

### Стоимость
- Перед генерацией — оценка стоимости по таблице цен реестра, показывается пользователю до подтверждения.
- После генерации — фактическая стоимость (если модель её возвращает) или расчёт по дельте баланса `/chat/credit` для батча.
- В шапке приложения — текущий баланс kie.ai и разметка "потрачено сегодня/за неделю".

## Дорожная карта

1. **Скелет проекта** — Vite+React+TS фронтенд, FastAPI бэкенд, Docker Compose (backend, frontend, Postgres), базовые модели SQLAlchemy + Alembic миграция, `.env` для `KIE_API_KEY`.
2. **Реестр моделей + форма генерации** — конфиг 3-5 моделей для старта (Flux-2, Imagen 4, Ideogram — легко расширяется), форма промта/стиля/размера/ориентации/назначения с пресетами, выбор моделей чекбоксами.
3. **Интеграция с kie.ai** — createTask/recordInfo клиент, параллельный запуск, скачивание и сохранение изображений локально, запись задач в БД, отдача статуса на фронт (поллинг).
4. **Экран результатов** — сетка сравнения по моделям, спиннеры для незавершённых, стоимость на карточку и суммарно, скачивание (по одной / zip всех).
5. **История/галерея** — список прошлых батчей с фильтрами (модель/стиль/дата), повтор промта с другим набором моделей.
6. **Полировка** — баланс kie.ai в шапке, обработка ошибок/таймаутов kie.ai, ретраи.

## Дополнительные идеи (сверх исходного запроса)
- Пресеты назначения изображения автоматически подставляют размер/ориентацию (см. выше).
- Сохранение любимых/оценённых генераций (лайк/рейтинг) — со временем видно, какая модель обычно лучше подходит под тип задачи.
- Библиотека промтов: сохранять и переиспользовать удачные промты, быстрый повтор с другим набором моделей.
- Seed / negative prompt там, где модель это поддерживает — для воспроизводимости результата.
- Несколько вариаций за один клик на модель (не только 1 картинка на модель).
- Дашборд расходов (день/неделя), предупреждение при низком балансе кредитов.
- Хранение оригинального ответа kie.ai (raw JSON) в БД на задачу — упростит отладку и добавление полей позже без миграции.
- Webhook от kie.ai вместо поллинга — снижает задержку и число запросов (можно добавить вторым шагом, поллинг как fallback).
- Storage-абстракция и реестр моделей с самого начала — единственные два места, которые реально придётся менять при переходе к продакшну (S3 вместо диска, много пользователей, очередь Celery/Redis вместо asyncio при большой нагрузке).

## Проверка
- Локальный запуск через `docker compose up`, ручная генерация по одному промту с 2-3 моделями, проверка: параллельность (общее время ≈ время самой долгой модели, а не сумма), корректность сохранённых файлов, отображение стоимости, скачивание.
- Проверка сценария ошибки одной из моделей (невалидные параметры/таймаут kie.ai) — остальные модели в батче должны отработать штатно.
- Проверка истории: генерация видна в списке после перезагрузки страницы/рестарта бэкенда.
